# bsp-service设计说明

# 1. 文档概述

## 1.1 设计目标

基于已实现的bsp-lib硬件抽象库，构建标准化的硬件服务化体系，核心目标为：

- 资源管控：对bsp-lib封装的硬件（LED、后续扩展的蜂鸣器/按键/摄像头等）进行统一生命周期管理，避免多应用抢占硬件资源；

- 通信标准化：采用ZeroMQ作为消息中间件，为上层应用提供统一、可靠的硬件访问接口，屏蔽底层硬件差异；

- 故障隔离：按硬件功能域拆分独立服务，单个硬件服务异常不影响整体系统稳定性；

- 可扩展适配：支持新增硬件服务快速集成，兼容bsp-lib的版本迭代；

- 运维友好：提供服务启停、状态监控能力，日志能力直接复用bsp-lib现有模块，降低运维成本。

## 1.2 核心选型说明

选用ZeroMQ作为消息中间件完全适配嵌入式Linux场景及本项目需求，核心优势如下：

- 轻量低耗：无中心服务依赖（点对点/发布订阅模式），部署包体积小，内存占用低，适配嵌入式资源受限设备；

- 多模式支持：支持REQ/REP（请求-响应，适配硬件指令交互）、PUB/SUB（发布-订阅，适配传感器数据推送）等多种通信模式，覆盖硬件交互全场景；

- 跨语言兼容：支持C/C++、Python等多种语言，上层应用可灵活选型开发；

- 高可靠性：内置消息队列、重连机制，适配嵌入式系统中不稳定的通信环境；

- 集成简单：API简洁，与C++代码集成友好，可快速对接服务化逻辑。

综上，ZeroMQ是本项目消息通信的最优选型，可满足“轻量、可靠、灵活”的嵌入式服务化通信需求。

## 1.3 适用场景

- 运行环境：嵌入式Linux系统（ARM/AArch64架构），与bsp-lib运行环境一致；

- 硬件范围：基于bsp-lib封装的所有硬件（当前为LED，后续扩展蜂鸣器、按键、摄像头、IMU、气压计、温湿度传感器）；

- 上层使用者：需要访问硬件资源的各类应用程序（如业务逻辑应用、监控应用等）；

- 核心交互场景：上层应用请求硬件控制（如LED开关）、上层应用订阅硬件数据（如温湿度、IMU数据）。

## 1.4 核心约束

- 开发语言：C++11及以上标准，与bsp-lib开发语言一致，降低集成成本；

- 依赖约束：仅依赖bsp-lib（硬件操作、日志功能）、ZeroMQ（消息通信）、cereal库（JSON序列化），无其他第三方重型依赖；

- 运行约束：服务以守护进程（daemon）形式运行，支持系统启动自启；

- 性能约束：硬件控制指令响应延迟≤10ms，传感器数据推送延迟≤50ms（可根据硬件类型配置）；

- 兼容性约束：兼容bsp-lib v1.0及以上版本，bsp-lib接口兼容升级时，服务层无需大幅修改。

# 2. 整体架构

## 2.1 架构分层

采用“三层架构+多服务拆分”模式，各层职责清晰，自上而下分别为：

1. 通信层：基于ZeroMQ实现消息收发、协议解析、连接管理，为上层应用提供标准化通信接口；

2. 服务层：按硬件功能域拆分独立服务，实现硬件资源管理、请求处理、数据采集与推送逻辑；

3. 硬件适配层：通过调用bsp-lib接口实现硬件操作，屏蔽底层硬件差异，是服务层与硬件的桥梁。

架构分层示意图：

上层应用 → 通信层（ZeroMQ）→ 服务层（多硬件服务）→ 硬件适配层（bsp-lib）→ 硬件设备

## 2.2 服务拆分原则

按“硬件功能域关联性、故障影响范围、资源占用特性”拆分服务，核心原则：

- 高关联硬件聚合：功能联动频繁的硬件归入同一服务（如LED、蜂鸣器、按键同属人机交互服务）；

- 故障隔离：高资源占用/高风险硬件独立服务（如摄像头服务，避免采集逻辑异常影响其他硬件）；

- 资源适配：同类型数据采集硬件聚合（如IMU、气压计、温湿度传感器同属传感服务，均为周期性采样）。

## 2.3 服务划分

结合当前及规划的硬件类型，拆分为3个核心服务，后续可按需扩展：

|服务名称|核心职责|管理硬件|通信模式（ZeroMQ）|
|---|---|---|---|
|输入输出服务（io-service）|处理输入输出类硬件的控制请求与状态读取，管理硬件并发访问，实现简单联动逻辑（如按键触发LED开关）|LED、蜂鸣器、按键|REQ/REP（控制请求、状态读取）|
|视觉服务（camera-service）|管理摄像头生命周期，处理图像采集、参数配置请求，推送图像数据|摄像头|REQ/REP（控制/配置）、PUB/SUB（图像数据推送）|
|传感服务（sensor-service）|管理各类传感器，实现周期性数据采集，处理采样率配置请求，推送传感器数据|IMU、气压计、温湿度传感器|REQ/REP（配置请求）、PUB/SUB（传感数据推送）|
## 2.4 核心交互流程

### 2.4.1 硬件控制流程（如LED开关）

1. 上层应用通过ZeroMQ的REQ模式发送控制指令（如“LED0打开”）至io-service；

2. io-service的通信模块解析指令，校验权限与参数合法性；

3. 服务核心模块调用bsp-lib的LED相关接口（如Led::turnOn()）；

4. bsp-lib执行硬件操作，返回结果给io-service；

5. io-service通过REP模式将操作结果反馈给上层应用。

### 2.4.2 传感器数据推送流程（如温湿度数据）

1. 上层应用通过ZeroMQ的SUB模式订阅sensor-service的传感数据主题；

2. sensor-service按配置的采样率，通过bsp-lib接口周期性采集温湿度数据；

3. sensor-service对采集的数据进行格式化处理；

4. 通过ZeroMQ的PUB模式将格式化数据推送至所有订阅的上层应用。

## 3.2 核心模块设计

### 3.2.1 通信层设计

#### 1. 封装类：ZmqComm

核心成员函数：

- bool init(ZmqMode mode, const std::string& addr)：初始化通信模式（REQ/REP/PUB/SUB）和地址（如tcp://*:5555）；

- int sendMsg(const std::string& msg)：发送消息，返回发送状态；

- int recvMsg(std::string& msg)：接收消息，返回接收状态；

- void subscribe(const std::string& topic)：SUB模式下订阅指定主题；

- void close()：关闭连接，释放资源。

#### 2. 通信协议

采用JSON格式封装消息（轻量、易解析），核心字段：

- 控制指令消息（REQ/REP）：{"cmd":"led_turn_on","dev_name":"led0","params":{},"seq":12345}

- 响应消息：{"code":0,"msg":"success","data":{},"seq":12345}（code=0成功，非0错误码）

- 数据推送消息（PUB/SUB）：{"topic":"temp_hum","dev_name":"temp_hum0","data":{"temp":25.5,"hum":60},"timestamp":1699999999}

说明：seq为消息序列号，用于请求与响应的对应；错误码与bsp-lib的ErrorCode对齐，便于问题定位。

### 3.2.2 服务层设计（以io-service为例）

每个服务均包含“服务核心”和“指令处理”两个子模块，职责分离：

#### 1. 服务核心模块（IoService）

核心职责：服务初始化、守护进程化、通信连接管理、请求分发、服务退出清理；

核心流程：

1. 读取配置文件（io_service.json），通过cereal库解析配置参数，初始化ZeroMQ通信（REP模式，绑定指定端口）；

2. 初始化bsp-lib硬件对象（LED、蜂鸣器、按键）

3. 将服务转为守护进程（fork子进程，脱离终端）

4. 循环接收上层应用请求，解析后分发至对应指令处理器

5. 接收指令处理结果，封装为响应消息反馈给上层应用

6. 捕获退出信号（如SIGINT、SIGTERM），执行资源清理（关闭硬件、释放通信资源）

#### 2. 指令处理模块（IoHandler）

核心职责：解析具体指令，调用bsp-lib接口执行硬件操作，处理联动逻辑；

支持指令及处理逻辑：

- led_turn_on/led_turn_off：调用Led::turnOn()/Led::turnOff()

- led_set_state：调用Led::setState()，参数为on/off

- beep_play：调用Beep::play()，参数为播放时长

- key_read：调用Key::readState()，返回按键状态

- key_bind_led：绑定按键与LED联动（如按键按下触发LED点亮）

### 3.2.3 硬件适配层设计

直接调用bsp-lib提供的C++接口，实现服务层与硬件的衔接，核心设计：

- 每个硬件对应一个封装对象（如LED对应bsp::Led类实例），由服务初始化时创建，退出时销毁；

- 对bsp-lib的返回值进行二次封装，映射为服务层的错误码，便于上层应用理解；

- 实现硬件资源锁机制（如std::mutex），避免多线程并发访问同一硬件导致的异常。

### 3.2.4 配置模块设计

采用JSON格式配置文件管理服务参数，使用cereal库实现JSON序列化与反序列化，支持运行时修改配置（需重启服务生效），核心配置项：

- 通信配置：ZeroMQ绑定地址（如tcp://*:5555）、消息超时时间；

- 硬件配置：硬件设备名与bsp-lib的映射关系（如"led0":"/dev/led0"）；

- 服务配置：传感器采样率、数据推送频率、服务日志级别；

- 容错配置：硬件重连次数、重连间隔。

### 3.2.5 日志模块设计

直接复用bsp-lib已实现的日志模块，无需重复开发，核心设计说明：

- 日志调用：服务层所有日志输出需求，直接调用bsp-lib提供的日志接口（如bsp::log::info()、bsp::log::error()）；

- 日志一致性：复用bsp-lib的日志级别（Debug、Info、Warn、Error）、日志格式及输出方式，保证全系统日志风格统一；

- 配置复用：日志输出目标（终端/文件/系统日志）、日志轮转规则等，直接沿用bsp-lib的配置，无需额外配置。

- 日志级别：与bsp-lib一致，支持Debug、Info、Warn、Error四级；

- 日志格式：[时间戳][服务名][级别] 内容（如2024-10-01 12:00:00 [hmi-service][INFO] 服务启动成功）；

- 日志输出：支持输出到终端、日志文件（/var/log/bsp-service/）、系统日志，可通过配置文件切换；

- 日志轮转：支持按大小/时间轮转日志，避免日志文件过大。

## 3.4 运维设计

### 3.4.1 服务启停管理

通过systemd实现服务自启与启停管理，以io-service为例，创建systemd服务文件（/etc/systemd/system/io-service.service）：

```ini
[Unit]
Description=BSP IO Service
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/io-service
ExecStop=/usr/bin/stop_all.sh io-service
Restart=on-failure  # 服务异常时自动重启
RestartSec=5s       # 重启间隔5秒
User=root
Group=root

[Install]
WantedBy=multi-user.target
```

启用自启命令：systemctl enable io-service

### 3.4.2 状态监控

service_monitor.sh脚本核心功能：

- 周期性检查各服务进程是否存活（ps -ef | grep 服务名）；

- 检查ZeroMQ通信端口是否正常监听（netstat -tuln | grep 端口号）；

- 监控日志文件，当出现Error级别日志时，触发告警（如输出到终端、发送邮件）；

- 生成监控报告，包含服务存活状态、资源占用（CPU/内存）、错误统计。

# 4. 测试与验证

## 4.1 单元测试

针对核心模块编写单元测试用例，重点测试：

- 通信模块：ZeroMQ不同模式的消息收发、连接断开重连；

- 指令处理模块：各类硬件指令的解析与执行、异常参数处理；

- 配置模块：JSON配置文件解析正确性（基于cereal库）、配置项有效性校验。

## 4.2 集成测试

测试服务端与客户端的完整交互流程，重点测试：

- 硬件控制流程：上层应用发送指令 → 服务接收解析 → 调用bsp-lib → 硬件执行 → 结果反馈；

- 数据推送流程：传感器采样 → 服务格式化数据 → 推送至订阅客户端；

- 并发访问：多个客户端同时请求同一硬件，测试服务的并发控制与资源锁有效性；

- 故障恢复：服务异常退出后，systemd自动重启功能验证；硬件断开重连功能验证。

## 4.3 性能测试

测试服务的响应延迟与吞吐量，核心指标：

- 控制指令响应延迟：≤10ms（如LED开关指令）；

- 传感器数据推送延迟：≤50ms（如温湿度数据，采样率10Hz）；

- 并发处理能力：支持≥10个客户端同时连接，无指令丢失或响应超时。

# 6. 总结

## 6.1 核心优势

- 架构清晰：分层设计+多服务拆分，职责明确，便于开发与维护；

- 通信可靠：基于ZeroMQ实现轻量、灵活的消息通信，适配嵌入式场景；

- 兼容扩展：与bsp-lib无缝衔接，支持硬件模块与服务的横向扩展；

- 运维友好：提供完善的启停、监控能力，复用bsp-lib日志模块，降低运维成本。

## 6.2 关键风险与应对

- 风险1：ZeroMQ消息队列堆积 → 应对：设置消息超时机制，定期清理过期消息，优化数据推送频率；

- 风险2：服务并发访问冲突 → 应对：实现硬件资源锁，严格控制并发访问；

- 风险3：bsp-lib版本升级导致兼容问题 → 应对：服务层与bsp-lib通过标准化接口对接，明确版本适配范围，升级前进行兼容性测试。

## 6.3 后续扩展

- 新增硬件服务：按现有服务架构，新增对应服务目录（如4g-service），复用通信、配置模块及bsp-lib日志模块；

- 通信加密：若需远程访问，可新增TLS加密模块，对ZeroMQ消息进行加密传输；

- 可视化监控：集成轻量级可视化监控工具，实时展示服务状态、硬件数据；

- 边缘计算能力：新增数据预处理模块（如传感器数据滤波、融合），降低上层应用处理压力。
